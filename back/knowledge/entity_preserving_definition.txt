Before generating Transformation Rules (TRs), the framework analyzes each R2RML Triples Map to determine whether it satisfies the entity-preserving property. Only entity-preserving mappings are automatically compiled into TRs. Mappings that do not satisfy this property are reported for manual analysis.
Entity-preserving Mappings
An R2RML mapping is entity-preserving if each RDF resource representing an instance of a class corresponds to exactly one tuple of a designated relation in the source database, called the pivot relation, and each pivot tuple generates at most one RDF resource. Thus, the mapping preserves the identity of the relational entities represented in the source schema.
This assumption is natural in schema mappings between relational databases and RDF. The purpose of an RDB2RDF mapping is to establish semantic correspondences between relational constructs and RDF vocabulary elements:
entity relations correspond to RDF classes;
relationships correspond to object properties;
attributes correspond to datatype properties.
Consequently, RDF resources should represent existing relational entities rather than new entities produced through aggregation, grouping, or other analytical transformations. Although the R2RML language permits arbitrary SQL queries in logical tables, including GROUP BY, DISTINCT, UNION, aggregation, and other relational operators, such mappings typically define analytical views rather than semantic correspondences between relational entities and RDF resources. Therefore, they fall outside the scope of the proposed framework.
The entity-preserving assumption establishes a one-to-one correspondence between relational entities and RDF resources, which constitutes the fundamental invariant underlying the incremental maintenance model and its correctness proofs.
Identifying the Pivot Relation
A Triples Map is entity-preserving if a pivot relation can be identified.
Formally, given an R2RML Triples Map, the analyzer determines whether there exists a relation R such that
every tuple of R generates exactly one RDF resource;
every generated RDF resource corresponds to exactly one tuple of R.
If such a relation exists, it is called the pivot relation of the mapping.
The corresponding Class Transformation Rule (CTR) associates tuples of the pivot relation with RDF instances of a class C. More precisely, the CTR establishes a semantic correspondence between a pivot tuple r and an RDF resource x, preserving the identity of the represented entity throughout the transformation.
In our formalism, the pivot relation associated with a transformation rule Ψ, denoted by pivot(Ψ), is the relation whose tuples serve as the starting point for constructing all RDF triples generated by Ψ. These tuples are called pivot tuples.
URI Construction from Pivot Tuples
The identity of the RDF resource generated by an entity-preserving mapping is determined by its pivot tuple.
Therefore, every entity-preserving R2RML mapping defines a function
f:R→URI
such that
each pivot tuple produces exactly one URI;
each generated URI corresponds to exactly one pivot tuple.
The URI constructor may use attributes stored directly in the pivot relation, as well as attributes obtained through functional foreign-key navigations rooted at the pivot tuple. However, every URI component must remain functionally determined by the pivot tuple so that the one-to-one correspondence is preserved.
Definition of URI_R

Let R be the pivot relation of an entity-preserving transformation rule, let r be a tuple variable ranging over R, and let s denote the source identifier.
The URI associated with r is defined by the URI constructor:
URI_R(r,s) ≡ hasURI(template, <e1,...,en>, s)
where
-  template denotes the URI template extracted from the R2RML Subject Map, 
- <e1,...,en> is the ordered sequence of pivot-rooted attribute expressions corresponding to the placeholders of the R2RML URI template;, and 
- s is the URI associated with the pivot tuple r.
Pivot-rooted attribute expressions have one of the following forms:
ei ::= r.A
ei ::= [FK(r,t)/t.A]
where r.A denotes an attribute of the pivot tuple, and [FK(r,t)/t.A] denotes the value of attribute A obtained after following the foreign key FK from the pivot tuple r to tuple t.
Definition of hasURI
hasURI(template, <e1,...,en>, s) iff
	s = instantiate(template, encode(eval(e1)), ..., encode(eval(en))).
 The instantiate function replaces each placeholder of the template with the encoded value obtained by evaluating the corresponding expression while preserving all constant fragments of the template.
Evaluation rules:
  eval(r.A) = r[A]
  eval([FK(r,t)/t.A]) = t[A], provided that FK(r,t) holds.
Example1: artist_tag Triples Map

R2RML map:
lb:artist_tag a rr:TriplesMap ;
  rr:logicalTable [rr:sqlQuery
    """SELECT artist.gid, tag.name
       FROM artist_tag
         INNER JOIN artist ON artist_tag.artist = artist.id          INNER JOIN tag ON artist_tag.tag = tag.id"""] ;   rr:subjectMap [rr:template "http://musicbrainz.org/artist/{gid} #tag/{name}";
                 rr:class muto:Tagging] ;
  rr:predicateObjectMap
    [rr:predicate muto:taggedResource ;
     rr:objectMap lb:sm_artist] ,
    [rr:predicate muto:hasTag ;
     rr:objectMap lb:sm_tag] .

rr:template "http://musicbrainz.org/artist/{gid}#tag/{name}"
Pivot relation: artist_tag
 URI predicate:
URI_artist_tag(r,s) ≡
hasURI(
  "http://musicbrainz.org/artist/{gid}#tag/{name}",
  <
    [artist_tag_fk_artist(r,a)/a.gid],
    [artist_tag_fk_tag(r,t)/t.name]
  >,
  s
)
Semantics:
s = instantiate(
      "http://musicbrainz.org/artist/{gid}#tag/{name}",
      encode(eval([artist_tag_fk_artist(r,a)/a.gid])),
      encode(eval([artist_tag_fk_tag(r,t)/t.name]))
	)
 
Assuming:
  a.gid = '8f3d4d52'
  t.name = 'Jazz'
the resulting URI is:
  http://musicbrainz.org/artist/8f3d4d52#tag/Jazz
This example illustrates that hasURI reproduces exactly the URI specified by the original R2RML template, while the values inserted into the placeholders are obtained through the pivot-rooted attribute expressions.
In this example, both URI components are obtained through explicit foreign-key navigations rooted at the pivot tuple. Although gid and name are not attributes of artist_tag, they are functionally determined by the pivot tuple.
Validity conditions: every URI component must be either a pivot attribute r.A or an FK-path attribute expression [FK(r,t)/t.A]. The foreign-key navigation must be functional from the pivot relation to the referenced relation.
Relationship with R2RML templates: every placeholder of an rr:template is translated into exactly one pivot-rooted attribute expression, preserving the URI prefix, placeholder order, and relational origin of each value.
Example 1 (Direct Pivot Attribute):
The URI associated with the pivot relation artist is defined as follows:
URI_artist(r,s) = hasURI("http://musicbrainz.org/artist/", <r.gid>, s)
